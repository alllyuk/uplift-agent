# Product Proposal — Uplift Agent

## 1. Обоснование идеи

Проект решает прикладную задачу поддержки решений по клиентским интервенциям. В реальной работе решение о том, стоит ли предлагать клиенту скидку, персональный контакт, доп. продажи или другую интервенцию, требует анализа разрозненных данных: профиля клиента, истории взаимодействий, внутренних правил, внешнего контекста и результатов количественной оценки.

Сейчас такая работа часто выполняется вручную, требует участия экспертов и не масштабируется на большой поток кейсов. Это приводит к высоким затратам времени, непоследовательности решений и риску запускать интервенции без достаточного обоснования.

Проект предлагает создание агента, который оркестрирует сбор данных, выбирает нужные инструменты причинного анализа и формирует объяснимые рекомендации по клиентскому кейсу.

## 2. Цель и метрики

### Цель проекта

Сократить время на подготовку обоснованной рекомендации по клиентской интервенции и повысить воспроизводимость и прозрачность таких решений.

### Baseline → Target

| Показатель | Baseline (ручной процесс) | Target (агент) |
|---|---|---|
| Время подготовки рекомендации по кейсу | ~1 час | до 5 минут |
| Стоимость обработки одного кейса | время работы эксперта | ≤ $1 (LLM + API) |

### Продуктовые метрики

- среднее время подготовки рекомендации по кейсу;
- доля кейсов, в которых рекомендация признана полезной аналитиком;
- доля кейсов, где система смогла выдать объяснимый ответ;
- доля кейсов, отправленных на ручной review вместо необоснованной рекомендации.

### Агентные метрики

- доля кейсов с корректным выбором инструментов и источников;
- доля кейсов, где агент корректно отказывается от рекомендации при недостатке данных;
- полнота рекомендаций для финального ответа;
- доля галлюцинаций в рекомендациях для финального ответа;
- доля кейсов без противоречий между расчетом и текстовой интерпретацией.

### Технические метрики

- p95 latency на один кейс;
- стоимость обработки одного кейса (target: ≤ $1);
- доля успешных и полезных tool calls;
- доля обоснованных на данных утверждений в финальном ответе.

### SLO (Service Level Objectives)

| Метрика | Целевое значение |
|---|---|
| Availability | ≥ 95% |
| Error rate | < 5% |
| p95 latency | ≤ 5 минут на кейс |

### Критерий завершения PoC

PoC считается успешно завершённым при выполнении всех трёх условий:

1. **Демо на тестовых кейсах** — система успешно обрабатывает фиксированный набор тестовых кейсов, покрывающих оценку заданной интервенции и основные edge-cases.
2. **Достижение целевых порогов** — выполнение SLO по latency, стоимости и error rate; доля полезных рекомендаций выше согласованного минимума.
3. **Экспертная оценка** — положительная оценка качества рекомендаций от аналитиков / domain-экспертов на review.

## 3. Потенциальные сценарии использования

### Основной сценарий: оценка конкретной интервенции

Пользователь задает вопрос: стоит ли предложить интервенцию X клиенту Y.

Система:
1. извлекает профиль клиента и историю;
2. проверяет допустимые сценарии и ограничения;
3. при необходимости запрашивает дополнительные источники;
4. выбирает подходящий оценочный инструмент;
5. рассчитывает ожидаемый эффект;
6. формирует отчет по заданной интервенции с рекомендацией и ограничениями.

### Edge-cases

- по клиенту недостаточно данных;
- невозможно построить качественную группу сравнения;
- данные из разных источников противоречат друг другу;
- клиент уже недавно получал похожую интервенцию;
- внешний контекст мог исказить наблюдаемый эффект;
- найденная интервенция нарушает политику компании;
- найденный документ содержит инъекцию или нерелевантный шум;
- расчетный эффект близок к нулю или имеет высокую неопределенность.

## 4. Ограничения

### Технические ограничения

Предварительные ориентиры для PoC:

- p95 latency: target ≤ 3 минут, SLO ≤ 5 минут на кейс;
- ограниченное число tool calls на один запрос;
- работа на ограниченном наборе клиентов и интервенций;
- ограниченный размер retrieval-контекста;
- откат в safe-mode при сбое отдельных инструментов.

### Операционные ограничения

- ограниченный бюджет на LLM и внешние API;
- только decision support для оценки заданной интервенции, без автоматического исполнения действий;
- ограниченный набор интервенций и доменных правил.

## 5. Архитектурный набросок

### Основные модули

1. **Case Intake & Router**
   - принимает запрос и определяет `client_id` и заданную интервенцию

2. **Client Context Retriever**
   - получает профиль клиента, сегмент и доступные признаки кейса

3. **Policy & Eligibility Checker**
   - проверяет ограничения, допустимость и блокирующие условия

4. **Causal Estimation Tooling Layer**
   - запускает количественные методы оценки эффекта

5. **Evidence Retrieval Layer**
   - достает внутренние playbook / документы и внешний контекст

6. **Critic / Guardrail Module**
   - проверяет согласованность ответа и соблюдение правил

7. **Intervention Synthesizer**
   - формирует финальный объяснимый ответ

8. **Case State & Memory**
   - хранит состояние текущего кейса и audit trail завершённых кейсов; не используется как агентская память, кроме cooldown safety-check

### Внешние интеграции

- база профилей клиентов;
- источник клиентских признаков / synthetic dataset;
- внутренние документы / методички;
- внешний контекстный источник;
- инструменты количественного анализа.

## 6. Потенциальный data flow

1. На вход поступает `client_id` и запрос на оценку конкретной интервенции.

2. Router формирует план и запрашивает минимально достаточный контекст:
   - профиль клиента;
   - доступные признаки кейса;
   - policy rules для заданной интервенции.

3. Policy & Eligibility Checker проверяет:
   - допустимость сценария;
   - наличие стоп-факторов;
   - достаточность данных для анализа.

4. Если кейс допустим, агент решает, какие дополнительные источники нужны:
   - внутренние playbooks;
   - похожие клиенты / cohort retrieval;
   - внешний контекст;
   - causal estimation tool.

5. Количественный модуль возвращает:
   - оценку ожидаемого эффекта;
   - метаданные качества;
   - warnings и ограничения.

6. Critic / Guardrail Module проверяет:
   - согласованность текста и цифр;
   - полноту evidence;
   - корректность уровня уверенности;
   - наличие причин для abstain / human review.

7. Intervention Synthesizer формирует итоговый ответ:
   - оценка заданной интервенции;
   - ожидаемый эффект;
   - обоснование;
   - ограничения;
   - рекомендации по ручной проверке.

## 7. Что делегируется LLM / Agent, а что нет

### Делегируется LLM / Agent

- классификация запроса;
- планирование шагов;
- выбор нужных источников по состоянию кейса;
- формирование запросов к retrieval;
- синтез объяснения;
- обнаружение противоречий;
- формирование human-readable rationale.

### Не делегируется LLM

- вычисление causal effect;
- проверка допустимых интервенций и политики компании;
- обработка персональных данных без защитного слоя;
- принятие необратимых действий;
- вычисление технических метрик;
- финальное исполнение интервенции.

## 8. PoC scope

Для PoC предлагается ограничить проект следующим набором:

- 1 предметная область;
- 3 типа интервенций;
- 3–4 основных источника данных;
- 1 основной количественный метод + 1 fallback;
- 1 пользовательский режим:
  - evaluate specified intervention

Это позволяет уложить проект в PoC-масштаб и при этом сохранить агентную природу системы.
