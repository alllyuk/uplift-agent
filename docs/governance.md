## 2. Политика логов

В системе логируются:

- факт запуска кейса;
- идентификатор кейса;
- какие модули и инструменты вызывались;
- статусы выполнения;
- технические ошибки и таймауты;
- метаданные качества расчета;
- итоговый тип результата:
  - evaluation;
  - abstain;
  - human review.

В логах не должны храниться:

- сырые персональные данные клиента;
- полные тексты чувствительных документов;
- открытые идентификаторы, если их можно заменить псевдонимами;
- лишние части prompt / retrieved context без необходимости диагностики.

Принципы логирования:

- data minimization;
- разделение технических логов и чувствительных артефактов;
- ограничение доступа к логам;
- возможность аудита по кейсу.

### Сроки хранения логов

| Тип логов | Срок хранения |
|---|---|
| Технические логи (ошибки, latency, health checks) | 90 дней |
| Аудитные трейсы кейсов (запуск, результат, модули, статусы) | 365 дней |

## 3. Политика работы с персональными данными

Если в проекте используются клиентские данные, система должна работать по принципу минимально необходимого доступа.

### Основные правила

- перед передачей данных в LLM по возможности удаляются или маскируются прямые идентификаторы;
- в prompt передаются только поля, необходимые для решения текущего кейса;
- доступ к данным ограничен ролями и назначением;
- чувствительные поля не используются без явной необходимости;
- для demo / PoC предпочтительно использовать синтетические или обезличенные данные.

### Для PoC

- допустимо использовать mock-данные или анонимизированные кейсы;
- реальные персональные данные не должны попадать в публичный репозиторий;
- отчеты и логи для демонстрации должны быть обезличены.

## 4. Шифрование

> В PoC шифрование не реализуется. Требования описаны как planned for production.

- **In transit:** все вызовы внешних API (OpenAI, retrieval-сервисы) должны выполняться по TLS.
- **At rest:** в production хранилища данных (БД, файловые системы с логами и индексами) должны использовать шифрование на уровне диска или СУБД.

## 5. RBAC (Role-Based Access Control)

> В PoC все функции доступны одному пользователю. Ролевая модель описана как planned for production.

Планируемые роли:

| Роль | Права |
|---|---|
| analyst | запуск кейсов, просмотр рекомендаций |
| reviewer | одобрение / отклонение рекомендаций, просмотр аудитных логов |
| admin | настройка системы, управление политиками, управление пользователями |

## 6. Регуляторика

> Для PoC, работающего на синтетических данных, регуляторные требования не применяются напрямую. Архитектура проектируется с учётом будущего соответствия.

При переходе на реальные данные система должна учитывать:

- **ФЗ-152** (О персональных данных) — локализация хранения ПД на территории РФ, согласие субъекта, минимизация данных.

## 7. Защита от injection и недоверенного контента

Все retrieved документы и внешние источники считаются недоверенным вводом.

### Базовые защиты

- инструкции внутри retrieved контента не могут менять поведение системных правил;
- retrieval-слой отделен от orchestration-логики;
- подозрительные фрагменты помечаются или отбрасываются;
- внешние источники используются как evidence, а не как управляющие инструкции;
- финальный ответ проходит critic-check на предмет нерелевантных или опасных утверждений.

## 8. Подтверждение действий

Для PoC агент не выполняет интервенции автоматически.

Он может только:

- оценить интервенцию;
- сформировать intervention evaluation report;
- отправить кейс на ручной review.

Любые действия, влияющие на клиента, должны требовать подтверждения человека вне рамок PoC.

## 9. Safe failure policy

Если система не может надежно завершить кейс, она должна перейти в безопасный режим, а не генерировать уверенный ответ.

### Safe failure cases

- недостаточно данных по клиенту;
- не найдено корректное сравнение для оценки эффекта;
- policy conflict;
- сбой ключевого инструмента;
- слишком высокая неопределенность результата;
- противоречие между источниками.

### Поведение в safe mode

- не рекомендовать интервенцию автоматически;
- явно указать причину ограничения;
- предложить ручную проверку или недостающие данные;
- сохранить trace кейса для последующего анализа.

## 10. Границы ответственности системы

Система предназначена для decision support, а не для автономного принятия бизнес-решений.

Поэтому:

- causal estimation выполняется отдельными инструментами, а не LLM “из головы”;
- LLM отвечает за orchestration и explanation;
- rule-based проверки обязательны для policy и eligibility;
- финальная интервенция вне PoC подтверждается человеком.
